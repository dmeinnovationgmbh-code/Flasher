# Connecting an interface: J2534 PassThru (Tactrix Openport & co.)

Most professional flashing hardware is a **J2534 PassThru** device: the vendor
ships a Windows DLL and *that DLL is the only way onto the bus*. `python-can`
does not speak J2534, so this toolkit has its own backend
([`med17flasher/core/j2534.py`](../med17flasher/core/j2534.py)).

Known-good with this backend's API level (J2534-1 v04.04): **Tactrix Openport
2.0**, Drew Technologies Mongoose, VXDIAG/VCX, Godiag, and any other device that
registers a PassThru driver.

> ⚠️ Read [`SAFETY.md`](SAFETY.md) before writing to a real ECU. Nothing in this
> toolkit has been validated on real hardware yet.

## 1. Install the vendor driver

The backend does not ship a driver — it uses the one you install.

* **Tactrix Openport 2.0**: install the *OpenPort 2.0 drivers* package from
  the vendor download page —
  <https://www.tactrix.com/index.php?Itemid=61>. It registers
  `op20pt32.dll` (typically under
  `C:\Program Files (x86)\OpenECU\OpenPort 2.0\drivers\j2534\`).
  The desktop app links to this page directly: a **"Tactrix-Treiber (Download)"**
  shortcut in the Start menu, and a note under the connection selector when no
  J2534 device is found.
* Other devices: their own installer does the same thing.

Registration means a key under `HKLM\SOFTWARE\PassThruSupport.04.04\` naming the
device and its `FunctionLibrary`. That is what we enumerate — both the 32- and
64-bit registry views, since most drivers register only in the 32-bit one.

## 2. Check it before you touch a car

```bash
med17flasher backends              # lists every installed PassThru interface
med17flasher j2534                 # opens it and reports firmware/DLL/API + battery
med17flasher j2534 --listen 5      # 5 s of passive traffic: proves the wiring works
```

`med17flasher j2534` prints the **battery voltage** the interface measures at
pin 16. Take it seriously: a MED17 that browns out mid-erase is a brick. Below
12 V, connect a charger before flashing.

`--listen` is the fastest way to tell "cable/ignition problem" from "ECU
problem": with the ignition on you should see plenty of frame ids. Nothing at
all means the bus is not connected, not that the ECU is dead.

## 3. Use it

Anywhere a backend is named — CLI or the app's transport dropdown:

```bash
med17flasher j2534                       # auto: the single installed device
med17flasher --backend j2534 identify
med17flasher --backend tactrix scan      # name aliases: tactrix / openport
med17flasher --backend "j2534:Openport" flash firmware.bin --profile med1775
med17flasher --backend "j2534:C:\path\to\op20pt32.dll" identify   # explicit DLL
```

The app's **Flashen** tab lists installed interfaces by their real name. When
none is installed the entry stays visible but greyed out, so you can see the
option exists rather than wondering where your tool went.

## 4. The 32-bit problem (and why it just works anyway)

Vendor PassThru DLLs are **32-bit**; `op20pt32.dll` says so in its name. The
desktop build is 64-bit, and the Windows loader refuses to map a 32-bit image
into a 64-bit process — `[WinError 193] %1 is not a valid Win32 application`.
No ctypes flag works around that.

So `open_j2534()` tries in-process first and, on exactly that error, falls back
to [`j2534_bridge.py`](../med17flasher/core/j2534_bridge.py): a **32-bit Python
helper process** owns the driver and relays frames over a line-JSON pipe. It is
the same mechanism the seed/key bridge uses (both share
[`procbridge.py`](../med17flasher/core/procbridge.py)).

For that fallback you need a **32-bit Python** installed (python.org's 32-bit
installer, or `py -3-32`). It is found automatically; pass `python32=<path>` to
override. `med17flasher j2534` prints `bits: 32` when the bridge is in use —
that is your proof the DLL really loaded.

Throughput is fine: a `recv` returns the driver's whole read batch in one reply,
so a pipe round trip is amortised over up to 16 frames.

## 5. Design notes

**Raw CAN, not ISO15765.** The channel is connected with `ProtocolID = CAN`, so
this toolkit's own tested ISO-TP layer does segmentation, flow control and
STmin. Letting device firmware do it instead would change timing and error
semantics per vendor, and the flash sequence depends on the behaviour we test.

**Two details bite everyone writing this the first time**, both handled here:

1. A freshly connected channel **receives nothing** until a `PASS_FILTER` is
   installed — the API blocks everything by default. We install a pass-all
   filter (mask 0 matches every id); in 29-bit mode, one for each width.
2. A CAN message's id is **the first 4 bytes of `Data`, big-endian**, not a
   struct field. `DataSize` counts `4 + len(payload)`.

**Other specifics:** `PASSTHRU_MSG` fields are `uint32` (Win32 `unsigned long`
is 32-bit even in a 64-bit process — `c_ulong` would be 64-bit on Linux and
shift every field). The device's transmit echo (`RxStatus & TX_MSG_TYPE`) is
dropped so ISO-TP never sees its own frames as ECU responses. A failed
`PassThruConnect` still calls `PassThruClose`, because a leaked handle locks the
interface until the driver unloads and the next run fails with
`ERR_DEVICE_IN_USE` for no visible reason.

## 6. Troubleshooting

| Symptom | Cause |
|---|---|
| `no J2534 PassThru device is installed` | Vendor driver not installed, or you are not on Windows. |
| `driver not found: ...op20pt32.dll` | Registered but the DLL is gone — reinstall the vendor package. |
| `not a J2534 PassThru driver (missing PassThruOpen)` | The path points at some other DLL. |
| `ERR_DEVICE_IN_USE` | Another program holds the interface (vendor tool, previous crash). Unplug/replug. |
| `[WinError 193]` and no 32-bit Python | Install 32-bit Python for the bridge (section 4). |
| Opens fine, `--listen` sees nothing | Ignition off, wrong OBD pins, or the ECU is on a different bus/bit rate. |
| `ERR_INVALID_BAUDRATE` | Device does not support the rate; MED17 diagnostics are 500 kbit/s. |

## Testing

[`tests/test_j2534.py`](../tests/test_j2534.py) compiles a **mock PassThru
driver in C** and runs the real ctypes layer against it: struct layout, the
big-endian id encoding, echo suppression, filters, batching, teardown order,
and the out-of-process bridge. The final test relays that mock onto a virtual
CAN network and drives a **complete UDS flash** — security access, erase, block
transfer, CRC verify — through the backend into the ECU simulator.

# MED17.7.5 (med1775) — real production flow

This maps a real MED17.7.5 calibration-flash flow onto the toolkit, using a
vendor **seed/key DLL** for Security Access. Ship profile:
[`config/med17_7_5_med1775.yaml`](../config/med17_7_5_med1775.yaml).

> Everything here writes to an ECU. Read [`SAFETY.md`](SAFETY.md) first, verify
> every address/value against your ECU/ODX, and only work on ECUs you are
> authorised to modify.

## The sequence

| # | Step | UDS | Notes |
|---|------|-----|-------|
| 1 | hard reset | `11 01` | `pre_hard_reset: true` |
| 2 | settle | — | `settle_delay: 10` s |
| 3 | programming session | `10 02` | `programming_session: 0x02` |
| 4 | request seed | `27 05` | `request_seed_level: 0x05` |
| 5 | send key | `27 06 <key>` | key from the DLL / seed-key server |
| 6 | fingerprint | `2E F15A 02…` | `fingerprints: when after_security` |
| 7 | erase | `31 01 FF00` | `erase_argument: none` (whole flash, no addr/size) |
| 8 | request download | `34 00 44 <addr> <len>` | ALFID 0x44 |
| 9 | fingerprint | `2E F15A 00…` | `fingerprints: when after_download` |
| 10 | transfer data | `36 …` | chunked by the negotiated block length |
| 11 | transfer exit | `37` | |
| 12 | (no checkMemory) | — | `verify_after_write: false` (checksum disabled) |
| 13 | hard reset | `11 01` | |
| 14 | diagnostic session | `10 03` | `final_session: 0x03` |
| 15 | clear DTC | `14 FF FF FF` | `clear_dtc_after: true` |

Two calibration transfer variants are valid; pick the one matching your file:

* `transferAddress 0x84002000`, `length 0x000FE000`
* `transferAddress 0x80140000`, `length 0x000C0000`

The calibration image must **start with `0x60` and end with `0xDE`** — validated
by `med17flasher.core.firmware.validate_calibration(data, length=…)`.

## Security Access via the seed/key DLL

The seed/key routine is a standard J2534 seed-key **DLL** (exports
`GenerateKeyExOpt`, `GetSeedLength`, `GetKeyLength`, `GetECUName`,
`GetConfiguredAccessTypes`). It is **32-bit stdcall**, so load it with 32-bit
Python on Windows (or under Wine). The DLL is your licensed asset — it is never
bundled here; point at it at runtime.

Three ways to use it:

```bash
# 1) directly on the flash (runs on the same 32-bit Windows host)
med17flasher flash --backend socketcan:can0 \
    --profile config/med17_7_5_med1775.yaml \
    --seedkey-dll MED1775_12_42_00.dll \
    calibration.bin

# 2) as a seed/key SERVER (run on 32-bit Windows; flasher may run anywhere) -
#    this matches a production getKey API:
med17flasher seedkey-server --dll MED1775_12_42_00.dll        # HTTP :8377 + TCP :8378
#    then, on the flashing host:
med17flasher flash --seedkey-server http://<win-host>:8377 ...
#    the server also answers the production-style route:
#      GET /key/05/<seedhex>  ->  {"key": "..."}

# 3) one-off key computation
med17flasher seedkey <seedhex> --dll MED1775_12_42_00.dll --level 0x05
```

An external `*-seed-key.exe` works too (`--exe cpcng-seed-key.exe` /
`--seedkey-exe …`), reading the key hex from stdout.

## Gateway / diagnostic firewall

Mercedes routes diagnostics through a gateway (EZS) that must be unlocked first.
Enable it in the profile (commented out by default):

```yaml
gateway:
  tx_id: 0x607
  rx_id: 0x587
  security_level: 0x39
  algorithm: med17     # or front it with its own DLL via a seed/key server
  params: {}
```

The flasher performs the gateway Security Access on `0x607/0x587` before the
main flow.

## Deriving the algorithm without the DLL

If you only have captured `(seed, key)` pairs (e.g. from a licensed tool), use
`seedkey-solve` to recover the algorithm/constants — see
[`SEEDKEY.md`](SEEDKEY.md).
